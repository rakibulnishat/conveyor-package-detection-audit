# From desktop to browser: a deployment and evaluation audit of a real-time conveyor package detection system

Code, data, raw results and figure scripts for the manuscript of the same title by
**Md. Rakibul Hasan Nishat** ([ORCID 0009-0009-2880-344X](https://orcid.org/0009-0009-2880-344X)) and
**Abdul Hasib** ([ORCID 0009-0000-6630-4240](https://orcid.org/0009-0000-6630-4240)).

Live web version: <https://nn-nishat.vercel.app/>

The system detects packages on a conveyor with YOLOv12s, raises an event when a package crosses a vertical line,
overlays an Eigen-CAM heat map on the package and asks a vision-language model (Groq) for a verdict. It exists in two
forms: a desktop application (PyTorch, every frame) and a web version (browser client + serverless ONNX function on
Vercel). The paper audits what changes between the two: prediction parity, JPEG transport, sampling rate and the
line rule, server latency, temporal leakage in the dataset split, and the faithfulness of the heat map.

**Scope.** The dataset has one class (`object`) and box annotations only. The experiments therefore measure package
localisation and deployment behaviour. They do **not** measure flap or damage detection, and the vision-language
verdict is not evaluated. All results come from one 191-frame clip (6.4 s, three packages).

## Environment

Every measurement in the paper was taken on one machine: Intel Xeon at 2.10 GHz, 2 virtual cores, 7.8 GiB RAM,
no GPU, Python 3.13.18, Node.js 22.23.4.

```bash
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements-experiments.txt
```

The deployed model was trained on a Colab GPU with `experiments/00_training/train_deployed_model.ipynb`
(Ultralytics 8.4.160 stored in the checkpoint). Everything else runs on CPU.

**API keys.** No key is stored in this repository. The desktop app and the web function read `GROQ_API_KEY` from the
environment; the notebook reads `ROBOFLOW_API_KEY`. Copy `apps/web/.env.example` to `apps/web/.env` for local runs and
never commit it.

## Running the applications

**Web version (local):**

```bash
cd apps/web
pip install -r requirements.txt uvicorn
uvicorn index:app --port 7861            # open http://localhost:7861
python tests/test_api.py                 # backend tests (Groq replaced by a fake client)
node tests/test_pipeline.js              # browser-side tracker, line rule and heat-map tests
```

Deployment to Vercel is described in `apps/web/DEPLOY_VERCEL.md`.

**Desktop application:**

```bash
cd apps/desktop
pip install -r requirements.txt groq
export GROQ_API_KEY=...                  # optional; without it the app falls back to local analysis
python video_app.py --source co.mp4
```

* **Step 9 and later** use the deployed ONNX path through `apps/web/pkginspect`. `parity/` was produced with ONNX
  Runtime 1.29.0 and `parity_ort1.30/` with 1.30.0 (the deployed version); boxes, scores and maps are identical, only
  the timing fields differ.
* **Step 17** needs the COCO-pretrained `yolo12s.pt` from the Ultralytics v8.4.0 release in
  `experiments/07_leakage/work/` (SHA-256 `e915c2c4286e3f6f8610ef106fa3f94a7b8c19b30eccede5887e22c33ef75f58`).
  Each condition takes about 65 min on the machine above (30 epochs, batch 4) and resumes from `last.pt` if
  interrupted. Both stored runs were resumed once after an environment restart (leaky from epoch 5, blocked from
  epoch 9), as logged in `experiments/07_leakage/preregistration.json`; a rerun from scratch will not reproduce the
  exact augmentation order. Training logs are in `results/leakage/train_logs_*`.
* **Step 19** also needs `yolo12s.pt` (the pretrained map in the weight-dependence comparison) and takes about
  1 h on one thread.
* **Step 15** writes `stream_q*.json`; running step 11's command on each of them gives `jpeg/web_rates_q*.json`.
* `parity/parity_summary.json` also carries four fields filled in after step 10: `cam_unrounded_max` and

  `desktop_track_boxes_conf_lt_025` (from `reference/pt_track.json`).
* **Rerun check.** Before release, steps 1–12, 15, 16, 18, 20 and 21 were rerun from this repository with ONNX
  Runtime 1.30.0. They reproduce the stored files exactly, apart from timing fields, the row order of boxes within a
  frame in `gt_boxes_by_frame.csv`, and the `times` field that the current `tracker_web_rates.js` adds. The figure
  scripts reproduce all 26 figures pixel for pixel. Steps 13, 14 and 19 report times that depend on the machine, and

## Data

`data/roboflow/` is version 1 of the Roboflow project
[`md-rakibul-hasan-nishat/object-hkkvs`](https://universe.roboflow.com/md-rakibul-hasan-nishat/object-hkkvs/dataset/1)
(licence CC BY 4.0), exported in YOLO format with Roboflow's preprocessing: auto-orientation and a 512x512 stretch
resize; no augmentation. It holds the 191 frames of `apps/web/public/co.mp4`, one image per video frame
(`results/dataset/dataset_vs_video.csv`), split at random by Roboflow into 134 training, 38 validation and 19 test
images with 323 boxes of one class.

Known issues, reported in the paper:

* Every validation and test frame has an adjacent frame in the training split, so the Roboflow split leaks.
* In frames 69, 70, 99, 110, 124 and 173 one box lies largely inside another. In frames 69 and 173 the outer box
  marks the tote and the inner box the carton inside it. Frame 173 is in the leakage test block.

Leakage-experiment splits (frame numbers are 1-based, as in the file names):

* test: odd frames 161–191 (16 frames), shared by both conditions
* validation: frames 4, 12, …, 116 (every eighth frame, 15 frames), shared
* time-blocked training: the remaining 108 frames from 1–123
* leaky training: the time-blocked set without 16 frames drawn with `random.Random(0).sample(blocked_train, 16)`
  (listed under `dropped_from_leaky`), plus the even frames 160–190, each adjacent to a test frame

## Known limitation of the desktop app

The desktop app attaches its Eigen-CAM hook to the model object it loads at start-up, while Ultralytics runs a copy
of that model inside its predictor. The hook therefore depends on how the predictor is set up. The parity reference
(`experiments/03_parity/e0_reference.py`) hooks the module the predictor actually executes.
